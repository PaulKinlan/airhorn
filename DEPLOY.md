# DEPLOY — what publishing this build would mean

Written for the V2 ship/no-ship decision (bead `airhorn-8uu`). Nothing has been
deployed: no DNS, no hosting, no credentials were touched. This is the record of
what **would** be published, how it is produced, and what local verification
cannot prove.

## What would be published

The entire contents of `dist/` — 26 files, 232,215 B (~232 KB) uncompressed,
~179 KB gzipped, measured from `preview/evidence.json` — uploaded **to the
root of an origin** — the service worker's scope is `/`, so it cannot be served
from a subdirectory without changing `public/sw.js` and the manifest scope.

Inventory (generated by `node tools/preview-evidence.mjs`, full byte counts in
`preview/evidence.json`):

- `index.html` — the app (11.97 kB, 4.06 kB gzip)
- `assets/index-*.js` — one hashed bundle (9.85 kB, 3.47 kB gzip); the hash
  changes every build
- `sw.js` — the service worker; build-stamped with `__BUILD_HASH__` and the
  exact asset list by the Vite plugin in `vite.config.js`
- `manifest.json` — install metadata (name, id, standalone display, 192/512 +
  maskable icons, screenshots, *Instant Blast* shortcut)
- `styles/main.css`, `sounds/airhorn.mp3`, `images/*` (icons + manifest
  screenshots), `favicon.ico`, `robots.txt`, `humans.txt`
- `.well-known/assetlinks.json` — **see the warning below**

## Build command

```bash
npm ci          # Node >= 20
npm run build   # -> dist/
```

`npm run preview` (or any static file server rooted at `dist/`) serves it
locally. That is the whole pipeline; there is no server-side component.

## Hosting requirements

1. **Origin root, HTTPS.** The SW registers with scope `/`; the manifest's
   `start_url` and `id` are root-anchored (`/?homescreen=1`). `127.0.0.1` and
   `localhost` are secure contexts, which is why the local checks below work;
   a real deployment needs a real certificate.
2. **`/sw.js` must not be cached hard.** Serve it with `Cache-Control:
   no-cache` (or a very short max-age). The cache name inside it is stamped
   with a hash of the whole build, so a re-fetched worker always gets a fresh
   cache and deletes the old one on activate; a stale worker file is the one
   thing that can freeze an old deployment in place.
3. **`/assets/*` may be immutable** (`Cache-Control: immutable, max-age=31536000`)
   — the filenames are content-hashed.
4. Correct MIME types for `.js`, `.css`, `.json`, `.webmanifest`-style JSON,
   `.mp3`, `.svg` (the local checkers send exactly these).

## What was verified locally (evidence in `preview/`)

All captured from a fresh-profile headless Chrome against a local `dist/`
server (`node tools/preview-evidence.mjs` after `npm run build`):

- **Renders**: light and dark colour schemes, and a 320 px mobile viewport
  (`horn-light.png`, `horn-dark.png`, `horn-320.png`).
- **Offline after first load**: with the network emulated dead, reload serves
  the whole app from the SW cache — horn at full size, CSS intact, no
  boot-failure alert (`horn-offline.png`, which also shows the app's own
  "No connection" banner). Press-and-hold still sounds it
  (`aria-pressed` true while held).
- **WebMCP with the flag on** (`--enable-features=WebMCP,WebMCPTesting`): the
  real `document.modelContext` exposes all three tools — `play_horn`,
  `stop_horn`, `get_horn_state` (recorded in `preview/evidence.json`).
- **Installability, static criteria**: manifest link present; manifest has
  name/short_name/id/start_url/scope, standalone display, 192 px, 512 px and
  maskable icons; service worker active with a fetch handler. **And the real
  `beforeinstallprompt` fired on `127.0.0.1`** — the browser considered the
  page installable, and the app enabled its Install button (visible in the
  light/dark screenshots).
- **Performance**: `preview/CWV-report.txt` (repo tool, CDP): cold load 92 KB
  transferred, FP ~104 ms, CLS 0.0000, INP p98 ~16 ms; repeat load 0 bytes over
  the network, everything SW-served, FP ~52 ms. The headless CDP tool does not
  report LCP.
- **Lighthouse: attempted, environment-incompatible — recorded, not hidden.**
  Nine full-page runs of Lighthouse 13.5.0 against the local server all failed
  with `NO_FCP`. This is not the page failing to paint: Lighthouse's own trace
  for the failing runs contains Paint events ~80 ms after navigation start, the
  captured screenshots show real renders, and the repo's CDP tool records FCP
  ~104 ms from `PerformanceObserver`. What never arrives is the
  `Page.lifecycleEvent: firstContentfulPaint` CDP event Lighthouse 13.5.0 waits
  on — a plain CDP session *does* receive it for the same markup, and a
  trivial page scores a full 100 under the same Lighthouse. Nine-plus runs
  (headless, and headed under Xvfb) never scored the full page, so **no
  Lighthouse score is claimed**; re-run Lighthouse on a desktop machine for
  the synthetic score (`npx lighthouse <deployed-url>`), and treat
  `preview/CWV-report.txt` as the perf evidence of record for this decision.

## What stays unverified without a real HTTPS deployment

- **Real-device install flow.** `beforeinstallprompt` firing on `127.0.0.1`
  proves Chrome's installability checker passed, but the mobile OS install
  banners, the standalone launch, and icon/splash rendering on Android/iOS are
  only provable on a served, certificated origin with real engagement
  heuristics in play.
- **`assetlinks.json` is the OLD production TWA's** (`com.airhorner.twa`,
  original signing-key fingerprint). If the existing Play-store TWA is not
  being reused as-is, this file will not match and must be regenerated (or
  removed) before publishing — a mismatch breaks deep links for the Android
  app, not the website.
- **Real-user CWV** (CrUX/RUM): everything above is synthetic, on a fast
  machine on loopback. Field data only exists after deployment.
- **The WebMCP flag**: production Chrome ships `document.modelContext` behind
  a flag; until it is on by default, real in-page agents are unverified in the
  wild (the code path itself is exercised by the repo's browser suites).

## Explicitly out of scope of this exercise

Deploying, DNS changes, hosting configuration, and any credential use. The
decision this pack supports is *whether* to ship, not the ship itself.
